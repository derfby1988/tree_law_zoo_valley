# แผนพัฒนาระบบ POS สำหรับ Tree Law Zoo Valley

เอกสารนี้ใช้เป็นทั้ง **แผนพัฒนา**, **รายการตรวจสอบการออกแบบ UX/UI**, และ **แนวทางออกแบบฐานข้อมูล** สำหรับระบบ POS ของ Tree Law Zoo Valley

## 1) เป้าหมายของระบบ

ระบบ POS ที่เหมาะกับแพลตฟอร์มนี้ควรตอบโจทย์ 5 เรื่องพร้อมกัน:

- **เร็ว** - ค้นหาและเพิ่มสินค้าได้ในไม่กี่คลิก
- **ชัด** - เห็นยอด, ภาษี, ค่าบริการ, ส่วนลด และยอดสุทธิแบบไม่ต้องเดา
- **ยืดหยุ่น** - รองรับขายหน้าร้าน, ฝากโต๊ะ, สั่งกลับบ้าน, จัดส่ง, และแยกการชำระเงิน
- **ตรวจสอบได้** - มีประวัติออเดอร์, ยกเลิก/คืนเงิน, บันทึกตรวจสอบ, และสต็อกที่ตามรอยได้
- **เหมาะกับบริบทสวนสัตว์/คาเฟ่** - ลูกค้าอายสั่งอาหาร, เครื่องดื่ม, ของที่ระลึก, และมีหลายจุดขาย

## 2) วิเคราะห์ UX/UI Flow ปัจจุบัน

### จุดแข็ง

- **โครงสร้างหน้าจอแบ่งโซนชัดเจน**
  - ซ้ายเป็นหมวดหมู่
  - กลางเป็นสินค้า
  - ล่างเป็นตะกร้า
  - ขวาเป็นการชำระเงิน
- **เหมาะกับหน้าจอ POS ขนาดใหญ่**
  - ดูข้อมูลพร้อมกันได้หลายส่วน
  - ใช้สีเน้นเดียวช่วยย้ำจุดสำคัญ
- **การคำนวณอัตโนมัติ**
  - ยอดรวมก่อนภาษี, ภาษี, ค่าบริการ, ยอดสุทธิ พร้อมแยกแสดง

### ช่องว่าง UX/UI ที่ควรปรับ

- **ยังไม่มีสถานะคำสั่งซื้อชัดเจน**
  - ไม่เห็นว่าออเดอร์เป็น ร่าง, ค้างชำระ, ชำระแล้ว, ยกเลิก, คืนเงิน
- **ยังไม่รองรับขั้นตอนการทำงานคีย์สำคัญของ POS จริง**
  - เปิดบิลค้างไว้
  - ย้ายโต๊ะ
  - แยกบิล
  - ลดราคาเฉพาะรายการ
  - เลือกประเภทคำสั่งซื้อตั้งแต่ต้น
- **ตะกร้ายังดูเป็นรายการเชิงเทคนิคมากกว่าเป็นกระบวนการขาย**
  - ยังขาดยอดรวมแยกตามหมวด/สรุปส่วนลด
  - ยังขาดหมายเหตุระดับรายการและระดับบิล
- **การชำระเงินยังเป็นปุ่มเลือกตามวิธีจ่าย**
  - เหมาะสำหรับกระบวนการง่าย แต่ยังไม่พอสำหรับแยกจ่าย, จ่ายบางส่วน, จ่ายผสม
- **ยังขาดการแจ้งเตือนสถานะ**
  - สินค้าหมด
  - ตะกร้าเกินสต็อก
  - ออเดอร์ถูกยืนยันสำเร็จแล้ว
  - การพิมพ์ใบเสร็จล้มเหลว

## 3) กระแส UX/UI ที่ควรมีสำหรับ Tree Law Zoo Valley

### 3.1 กระแสหลัก: ขายหน้าร้าน

1. เลือก **ประเภทการขาย**
   - ทานที่ร้าน
   - กลับบ้าน
   - เดลิเวอรี
   - บริจาค/สวัสดิการพนักงาน (ถ้ามีใช้จริง)

2. เลือก **ลูกค้า/โต๊ะ/บิล**
   - เดินเข้ามาใหม่ = สร้างบิลใหม่
   - มีโต๊ะ = ผูกโต๊ะ
   - มีลูกค้าสมาชิก = ผูกโปรไฟล์ลูกค้า

3. เลือกสินค้า
   - หมวดหมู่ด้านซ้าย
   - ค้นหาด้วยชื่อ/บาร์โค้ด
   - มีปุ่มเพิ่มด่วนสำหรับสินค้าขายดี

4. ตรวจสอบตะกร้า
   - เพิ่ม/ลดจำนวน
   - ใส่หมายเหตุรายการ
   - แก้ไขส่วนลดเฉพาะบิลหรือเฉพาะรายการ

5. ชำระเงิน
   - เงินสด / บัตรเครดิต / โอน / QR / แยกการชำระ
   - ตรวจยอดค้างชำระก่อนยืนยัน

6. ปิดงาน
   - พิมพ์ใบเสร็จ
   - บันทึกสต็อก
   - บันทึกประวัติการตรวจสอบ

### 3.2 กระแสที่ควรเพิ่ม

- **พักบิล** - ฝากบิลไว้ก่อน
- **เรียกบิลคืน** - กลับมาเปิดบิลเดิม
- **ยกเลิก / คืนเงิน** - ต้องมีเหตุผลและสิทธิ์กำกับ
- **ย้ายโต๊ะ** - เปลี่ยนโต๊ะโดยไม่ต้องสร้างออเดอร์ใหม่
- **แยกรายการ / แยกบิล** - แบ่งรายการหรือแบ่งยอดออกเป็นหลายส่วน

## 4) ข้อเสนอ UX/UI ที่เหมาะกับ Tree Law Zoo Valley

### 4.1 หน้าจอควรเปลี่ยนจาก 5 โซนเป็น 6 บล็อกเชิงการทำงาน

- **แถบข้อมูลบิล**
  - ประเภทการขาย
  - โต๊ะ
  - ลูกค้า
  - พนักงาน
  - สถานะบิล

- **แถบหมวดหมู่**
  - หมวดสินค้า
  - รายการโปรด
  - สินค้าขายดี

- **ตัวเลือกสินค้า**
  - ค้นหา
  - สแกนบาร์โค้ด
  - เพิ่มด่วน
  - ป้ายแจ้งสต็อก/หมด

- **ตะกร้าและการปรับยอด**
  - รายการสินค้า
  - หมายเหตุ
  - ส่วนลด
  - ภาษี
  - ค่าบริการ

- **แผงชำระเงิน**
  - เลือกวิธีจ่าย
  - แยกการชำระ
  - ยกเลิก/คืนเงิน

- **แถบปุ่มดำเนินการ**
  - พักบิล
  - บันทึกฉบับร่าง
  - พิมพ์ใบเสร็จ
  - ยืนยันปิดบิล

### 4.2 รูปแบบ UX ที่ควรเพิ่ม

- **ค้นหาด่วนที่เด่นกว่าเดิม**
  - รองรับพิมพ์ชื่อสินค้า, บาร์โค้ด, รหัสสินค้า

- **สินค้าแนะนำตามสถานการณ์**
  - เช้า: เครื่องดื่ม/เบเกอรี่
  - เที่ยง: อาหารหลัก
  - เด็ก/ครอบครัว: ชุด/เมนูยอดนิยม

- **สถานะสีที่สอดคล้องกัน**
  - เขียว = พร้อมขาย/ชำระแล้ว
  - เหลือง = ต้องตรวจสอบ
  - แดง = หมด/ผิดพลาด/ยกเลิก

- **สถานะว่างที่มีการนำทางต่อ**
  - ไม่มีสินค้า -> แนะนำค้นหา/เลือกหมวด
  - ตะกร้าว่าง -> ปุ่มเรียกร้องการกระทำที่ชัด

## 5) โครงสร้างข้อมูลที่ควรมีจริง

### 5.1 ตารางหลักสำหรับ POS

#### `pos_orders`
เก็บหัวบิลทุกใบ

ควรมีฟิลด์สำคัญ:
- `order_number`
- `order_type` (`dine_in`, `takeaway`, `delivery`)
- `status` (`draft`, `held`, `pending_payment`, `paid`, `voided`, `refunded`, `partially_refunded`)
- `table_id`
- `customer_id`
- `cashier_id`
- `subtotal`
- `discount_total`
- `tax_total`
- `service_total`
- `grand_total`
- `paid_total`
- `balance_due`
- `notes`
- `opened_at`, `closed_at`

#### `pos_order_items`
เก็บรายการสินค้าแต่ละบิล

ควรมีฟิลด์สำคัญ:
- `order_id`
- `product_id`
- `product_name_snapshot`
- `unit_price_snapshot`
- `quantity`
- `line_discount`
- `tax_rate_snapshot`
- `service_rate_snapshot`
- `tax_exempt`
- `item_note`
- `line_total`

#### `pos_payments`
เก็บการจ่ายเงินจริงทุกครั้ง

ควรมีฟิลด์สำคัญ:
- `order_id`
- `payment_method`
- `amount`
- `reference_number`
- `paid_at`
- `status`
- `received_by`

#### `pos_discounts`
ส่วนลดระดับบิล/รายการ

ควรมีฟิลด์สำคัญ:
- `discount_type`
- `scope` (`order`, `item`, `category`)
- `value`
- `max_discount`
- `min_amount`
- `stackable`
- `start_at`, `end_at`
- `is_active`

#### `pos_order_discounts`
เชื่อมว่าบิลนี้ใช้ส่วนลดอะไรบ้าง

#### `pos_taxes`
เก็บนโยบายภาษีที่ระบบใช้จริง

ควรมีฟิลด์สำคัญ:
- `name`
- `rate`
- `is_inclusive`
- `applies_to`
- `is_exempt`
- `jurisdiction`

#### `pos_service_charges`
เก็บค่าบริการและกติกาการคิด

#### `pos_tables`
ถ้ามีโต๊ะ ต้องแยกตารางนี้ออกมา

ควรมีฟิลด์สำคัญ:
- `table_code`
- `zone`
- `status`
- `capacity`
- `current_order_id`

#### `pos_customers`
โปรไฟล์ลูกค้าและสมาชิก

#### `pos_order_status_logs`
บันทึกการเปลี่ยนแปลงสถานะบิล

#### `pos_void_refunds`
บันทึกการยกเลิก/คืนเงิน พร้อมเหตุผลและผู้อนุมัติ

#### `pos_shift_sessions`
รอบกะของแคชเชียร์

#### `pos_register_cash_drawers`
เงินสดเข้าออกของเครื่องแคชเชียร์แต่ละเครื่อง

#### `pos_printer_profiles`
การตั้งค่าเครื่องพิมพ์ต่อจุดขาย

#### `pos_audit_logs`
บันทึกการเปลี่ยนแปลงทุกการดำเนินการสำคัญ

### 5.2 ตารางเสริมสำหรับแพลตฟอร์ม Tree Law Zoo Valley

- **`pos_menu_groups`** - แบ่งเมนูตามช่วงเวลา/ธีม
- **`pos_bundle_promotions`** - ชุดโปรโมชั่น เช่น เมนูคู่, เซ็ตครอบครัว
- **`pos_loyalty_wallets`** - สะสมแต้ม/เครดิตสมาชิก
- **`pos_store_settings`** - ค่าระบบระดับสาขา
- **`pos_device_sessions`** - เครื่อง POS เครื่องไหนเปิดใช้
- **`pos_inventory_reservations`** - กันสต็อกเมื่อเปิดบิลค้างไว้

## 6) โครงสร้างฐานข้อมูลที่แนะนำให้ปรับจากของเดิม

### ของเดิมที่ควรขยาย

- `pos_orders`
  - ตอนนี้ควรรองรับหลายสถานะ ไม่ใช่แค่สถานะเสร็จสิ้น
- `pos_order_lines`
  - ควรเก็บสแนปชอตของราคา, ภาษี, หน่วย, หมายเหตุ
- `inventory_products`
  - ควรแยกจำนวนที่ขายได้จริงกับจำนวนที่จองไว้
- `inventory_adjustments`
  - ควรมีประเภทอ้างอิงที่ชัดว่ามาจาก ขาย, คืนเงิน, ยกเลิก, โอนย้าย

### ความสัมพันธ์ที่ควรมี

- 1 ออเดอร์ → หลายรายการสินค้า
- 1 ออเดอร์ → หลายการชำระเงิน
- 1 ออเดอร์ → หลายส่วนลด
- 1 ออเดอร์ → หลายบันทึกสถานะ
- 1 กะ → หลายออเดอร์
- 1 ลูกค้า → หลายออเดอร์
- 1 โต๊ะ → 1 ออเดอร์ที่ใช้งานอยู่ได้ในช่วงเวลาเดียว

## 7) สิ่งที่ขาดในกระแสโค้ดปัจจุบัน

### ฝั่ง UI

- **ไม่มีลิ้นชักออเดอร์ / สรุปออเดอร์ที่จัดการสถานะได้จริง**
- **ยังไม่มีปุ่มพักบิล / เรียกบิลคืน**
- **ยังไม่มีตัวเลือกลูกค้า**
- **ยังไม่มีหน้าต่างแยกการชำระ**
- **ยังไม่มีพรีวิวใบเสร็จ**
- **ยังไม่มีป้ายแจ้งสต็อกต่ำบนสินค้า**

### ฝั่งตรรกะ

- **ยังคำนวณภาษี/ค่าบริการแบบรวม**
  - ควรคำนวณระดับรายการเพื่อตรวจสอบได้
- **ยังไม่มีระบบจัดการสถานะการชำระ**
  - รอชำระ -> ชำระบางส่วน -> ชำระครบ
- **ยังไม่มีกระแสคืนเงิน**
  - คืนเงินควรเป็นธุรกรรมใหม่ ไม่ใช่แค่ลบรายการ
- **ยังไม่มีการควบคุมกะ**
  - POS จริงต้องรู้ว่าใครเปิดเครื่องกะไหน

## 8) แผนพัฒนา (อัปเดตสถานะจริง — ตรวจสอบโค้ด 13 ส.ค. 2026)

> **หมายเหตุ:** สถานะต่อไปนี้ได้รับการตรวจสอบโดยการอ่านซอร์สโค้ดจริง ไม่ใช่การประมาณการ

### ระยะที่ 1 - ความเสถียรของ POS หลัก

1. **ชั้นข้อมูลบริบทออเดอร์** [✅ เสร็จและทำงานได้จริง]
   - ประเภทคำสั่งซื้อ, โต๊ะ, โซน, ลูกค้า, พนักงานผู้รับผิดชอบ, แคชเชียร์ ผูกครบในส่วนหัว
   - รองรับผ่าน `pos_page.dart` + `table_management_service.dart` + `supabase_service.dart`

2. **เครื่องงานตะกร้าและราคา** [✅ เสร็จแล้ว]
   - ภาษีระดับรายการ ✅ คำนวณถูกต้องตามกฎภาษีต่อหมวดสินค้า
   - ค่าบริการ ✅ ดึงจากโซนโต๊ะอัตโนมัติ
   - **ส่วนลดสมาชิก (`_discount`)** ✅ ผูกกับ `_redeemedPoints * AppBusinessSettings.pointValueRatio` เรียบร้อยแล้ว
   - ส่วนลดระดับรายการ ❌ ยังไม่มี (ส่วนลดทำได้เฉพาะระดับบิล)

3. **กระแสสถานะการชำระเงิน** [✅ เสร็จแล้ว]
   - ชำระเต็มจำนวน, แยกการชำระ ✅ ทำงานได้
   - `PosPaymentSplitService` ✅ บันทึกการแยกชำระลง `pos_payment_splits`
   - **การบังคับเปิดกะก่อนปิดบิล** ✅ เรียก `_ensureShiftIsOpen()` ตรวจสอบสถานะกะและบังคับเปิดกะก่อนเปิด Payment Dialog

4. **พัก / เรียกบิลคืน** [✅ เสร็จและทำงานได้จริง]
   - `PosHeldOrderService`: พักบิล, เรียกบิลคืน, ยกเลิกบิลพัก, ดึงบิลพักตามโต๊ะ ครบ
   - UI: หน้าต่างพักบิล, รายการบิลที่พัก, กู้คืนตะกร้า + ส่วนลด ครบ

### ระยะที่ 2 - ความครบถ้วนทางธุรกิจ

5. **ลูกค้าและสะสมแต้ม** [✅ เสร็จแล้ว]
   - `PosCustomerPickerWidget` ✅ และ `PosLoyaltyDisplayWidget` ✅ แสดงในโซน 3
   - **การแลกแต้มสมาชิก** ✅ หักส่วนลด `_discount` ออกจากยอดสุทธิเรียบร้อยแล้ว

6. **เครื่องงานส่วนลดและโปรโมชั่น** [⚠️ เสร็จบางส่วน]
   - ส่วนลดระดับบิลผ่าน `PosDiscountPanelWidget` ✅
   - `pos_discount_service.dart` + `pos_promotion_service.dart` ✅
   - ส่วนลดระดับรายการ ❌ ยังไม่มี

7. **ใบเสร็จและการพิมพ์** [⚠️ เสร็จ UI — ยังไม่ผ่านฮาร์ดแวร์]

### 🔍 9.1 วิเคราะห์ผลกระทบเชิงลึกและแนวทางการแก้ปัญหาสำหรับ P0 (ผลกระทบ P0 และแนวทางแก้ไขที่ดีที่สุด)

เอกสารส่วนนี้บันทึกผลการวิเคราะห์จากซอร์สโค้ดจริง เพื่อเป็นคู่มือมาตรฐานในการแก้ไขปัญหาความเสี่ยงระดับวิกฤต (P0 บั๊กวิกฤต)

#### 🔴 P0-1a: ผูก `_discount` กับ `_redeemedPoints` จริง
* **ตำแหน่งไฟล์**: `lib/pages/pos_page.dart` (L514)
* **สภาพปัญหาจากโค้ดจริง**:
  * `double get _discount => 0;` ถูกฮาร์ดโค้ดค่าเป็น 0
  * แม้ผู้ใช้จะเลือกแต้มสะสมสมาชิกใน `_redeemedPoints` แต่ `_discount` ไม่ถูกคำนวณเปลี่ยนเป็นมูลค่าบาท
  * ผลลัพธ์คือ `_preTaxTotal = _subtotal - _discount - _totalDiscountAmount` คำนวณยอดชำระโดยไม่หักส่วนลดสมาชิก
* **ผลกระทบ**:
  * **บกพร่องทางบัญชี**: ลูกค้าเสียแต้มฟรีโดยไม่ได้รับส่วนลดจริง หรือพนักงานต้องลดราคาเองทำให้ยอดเงินสดในลิ้นชักไม่ตรงกับระบบบิล
* **แนวทางแก้ไขที่ดีที่สุด**:
  1. แก้ไข getter `_discount` ใน `pos_page.dart` ให้คำนวณจาก `_redeemedPoints * AppBusinessSettings.pointValueRatio` (เช่น 1 แต้ม = 1 บาท)
  2. อัปเดต `_preTaxTotal` และ `_netTotal` ให้สะท้อนยอดหลังหักแต้มสะสมทันที
  3. ส่ง `loyaltyPointsRedeemed: _redeemedPoints` และ `loyaltyDiscountAmount: _discount` ไปยัง `InventoryService.createPosOrder()` เพื่อบันทึกแยกประเภทส่วนลดลง DB ชัดเจน

### 🔍 9.3 วิเคราะห์ผลกระทบเชิงลึกและแนวทางการแก้ปัญหาสำหรับ Priority 2 (ผลกระทบ Priority 2 และแนวทางแก้ไขที่ดีที่สุด)

งานกลุ่ม Priority 2 เน้น **ความสมบูรณ์แบบในการปฏิบัติงานหน้าร้าน (ประสบการณ์การปฏิบัติงานหน้าร้าน), การป้องกันความผิดพลาดของแคชเชียร์, และการเชื่อมต่อฮาร์ดแวร์จริง**

#### 🟡 P2-2a: ป้ายสต็อกต่ำบนการ์ดสินค้าในกริด
* **ตำแหน่งไฟล์**: `lib/pages/pos_page.dart` (`_buildZone4()` / `_buildProductCard`)
* **สภาพปัญหาจากโค้ดจริง**:
  * การ์ดสินค้าในกริดแสดงเฉพาะชื่อและราคา ไม่แสดงจำนวนคงเหลือในคลัง
  * แคชเชียร์สามารถกดเลือกสินค้าที่หมดแล้วเข้าตะกร้าได้ แล้วค่อยโดนบล็อกตอนปิดบิล
* **ผลกระทบ**:
  * **แคชเชียร์เสียเวลา**: เลือกสินค้าใส่ตะกร้าแล้วต้องมากดลบออกภายหลังเมื่อรู้ว่าไม่มีสินค้าในคลัง
* **แนวทางแก้ไขที่ดีที่สุด**:
  1. ดึง `product['quantity']` และ `product['min_quantity']` มาตรวจสอบในการ์ดสินค้า
  2. สต็อก = 0: แสดงป้ายสีแดง **"สินค้าหมด"**, ปรับการ์ดจางลง (ความโปร่งแสง 0.5), และปิดการแตะ
  3. สต็อก <= จำนวนขั้นต่ำ: แสดงป้ายสีส้ม **"คงเหลือ X ชิ้น"** เพื่อเตือนแคชเชียร์ล่วงหน้า

#### 🟡 P2-2b: UI แก้ไขหมายเหตุรายการในตะกร้า
* **ตำแหน่งไฟล์**: `lib/pages/pos_page.dart` (`_buildZone5()`)
* **สภาพปัญหาจากโค้ดจริง**:
  * โครงสร้าง `_cartItems` มีคีย์ `'note'` และตาราง `pos_order_lines` มีคอลัมน์ `note` รองรับแล้ว
  * แต่ใน UI แผงตะกร้าขาดปุ่ม/ช่องข้อความให้แคชเชียร์พิมพ์หรือเลือกหมายเหตุรายการสินค้า
* **ผลกระทบ**:
  * **ขาดความยืดหยุ่นหน้าร้าน**: ไม่สามารถระบุรายละเอียดเฉพาะของลูกค้าได้ เช่น "หวานน้อย", "แยกน้ำแข็ง", "ไม่เผ็ด"
* **แนวทางแก้ไขที่ดีที่สุด**:
  1. เพิ่มไอคอนแก้ไขหมายเหตุบนแถวสินค้าในแผงตะกร้า
  2. เมื่อกด ให้เด้งตัวเลือกลัด (เช่น [หวานน้อย] [แยกน้ำแข็ง] [ไม่ใส่ผัก]) พร้อมช่องพิมพ์ข้อความเพิ่มเติม
  3. บันทึกลง `item['note']` เพื่อส่งไปบันทึกลงฐานข้อมูลและพิมพ์แสดงผลบนใบเสร็จ/สลิปห้องครัว

#### 🟡 P2-2c: ค้นหาบาร์โค้ดผูกกับแคตตาล็อกสินค้าจริง
* **ตำแหน่งไฟล์**: `lib/pages/pos_page.dart` (`_barcodeController` & `_onBarcodeSubmitted`)
* **สภาพปัญหาจากโค้ดจริง**:
  * มี `_barcodeController` แล้ว แต่ยังไม่ได้ผูกตรรกะค้นหาและเพิ่มสินค้าลงตะกร้าอัตโนมัติเมื่อปืนสแกนส่งรหัสบาร์โค้ดเข้าช่องค้นหา
* **ผลกระทบ**:
  * **การขายหน้าร้านช้า**: ไม่สามารถใช้ปืนสแกนบาร์โค้ดได้ พนักงานต้องพิมพ์ค้นหาชื่อสินค้าด้วยมือเท่านั้น
* **แนวทางแก้ไขที่ดีที่สุด**:
  1. ผูก `onSubmitted` ในช่องข้อความค้นหาบาร์โค้ดให้ค้นหาใน `products` ด้วย `barcode == code` หรือ `sku == code`
  2. หากเจอสินค้า: เพิ่มสินค้าเข้าตะกร้าทันที 1 ชิ้น แล้วเคลียร์ช่องค้นหาเพื่อพร้อมสแกนชิ้นถัดไป
  3. หากไม่เจอ: แสดงข้อความแจ้งเตือน "ไม่พบสินค้าบาร์โค้ด: $code"

#### 🟡 P2-2d: ทดสอบการพิมพ์ด้วยฮาร์ดแวร์กับเครื่องพิมพ์จริง
* **ตำแหน่งไฟล์**: `lib/services/pos_printer_service.dart`
* **สภาพปัญหาจากโค้ดจริง**:
  * `PosPrinterService` เขียนระบบสั่งพิมพ์ผ่าน ESC/POS TCP/IP และ PDF ไว้แล้ว แต่ยังไม่เคยผ่านการสอบทานบนเครื่องพิมพ์ความร้อน (เครื่องพิมพ์ความร้อน 80มม./58มม.) จริง
* **ผลกระทบ**:
  * **เสี่ยงพิมพ์สลิปไม่สำเร็จ**: ภาษาไทยอาจเพี้ยน/สระลอย, กระดาษไม่ถูกตัดอัตโนมัติ (คำสั่งตัดกระดาษ), หรือสัญญาณเปิดลิ้นชักเก็บเงิน (สัญญาณเปิดลิ้นชัก) ไม่ทำงาน
* **แนวทางแก้ไขที่ดีที่สุด**:
  1. ทดสอบการเชื่อมต่อกับเครื่องพิมพ์สลิปจริงผ่านเครือข่ายแลน/WiFi ที่อยู่ IP
  2. ทดสอบชุดคำสั่งตัดกระดาษ (`GS V 66 0`) และคำสั่งสั่งเด้งลิ้นชักเก็บเงิน (`ESC p 0 25 250`)
  3. สร้างระบบสำรอง: หากการสั่งพิมพ์แบบเครือข่าย TCP ขัดข้อง ให้สลับไปใช้หน้าต่างพิมพ์ PDF ของระบบแทนอัตโนมัติ


- ใช้เป็น **รายการตรวจสอบฐานข้อมูล** ก่อนเพิ่มการย้ายข้อมูล
- ใช้เป็น **ลำดับการพัฒนา** เพื่อไม่ให้ POS โตแบบไร้โครงสร้าง
- ใช้เป็น **บันทึกความจำ** ว่าระบบนี้ต้องพร้อมใช้งานจริงสำหรับ Tree Law Zoo Valley

## 11) วิเคราะห์ `lib/pages/pos_page.dart` แบบลงลึกทีละฟังก์ชัน

เอกสารส่วนนี้จับคู่ฟังก์ชันจริงใน `pos_page.dart` กับแผนพัฒนา เพื่อใช้เป็นแนวทางรีแฟกเตอร์ทีละขั้น โดยเรียงจากฟังก์ชันพื้นฐาน → ฟังก์ชันคำนวณ → ฟังก์ชัน UX → ฟังก์ชันปิดบิล

### 11.1 โครงสร้างสถานะและวงจรชีวิต

- `initState()`
  - หน้าที่ปัจจุบัน: ผูก focus listener และเริ่มโหลดข้อมูล
  - สิ่งที่ดี: ทำให้หน้า POS พร้อมใช้งานทันทีเมื่อเปิดหน้า
  - สิ่งที่ยังขาด: สถานะข้อผิดพลาด, ลองใหม่, สถานะว่าง, การโหลดแบบทีละขั้น
  - แผนที่เกี่ยวข้อง: ระยะที่ 1 - ตัวเลือกสินค้า, ชั้นข้อมูลบริบทออเดอร์
  - แนวทางรีแฟกเตอร์: ย้ายการโหลดข้อมูลออกจากหน้าไปยังคอนโทรลเลอร์/พื้นที่เก็บข้อมูล และเพิ่มโมเดลสถานะแบบ `กำลังโหลด / โหลดแล้ว / ว่าง / ผิดพลาด`

- `dispose()`
  - หน้าที่ปัจจุบัน: ปล่อยคอนโทรลเลอร์และ focus node
  - สิ่งที่ดี: การทำความสะอาดถูกต้อง
  - สิ่งที่ยังขาด: ถ้าเพิ่มคอนโทรลเลอร์การชำระ/ลูกค้า/โต๊ะ ต้องรวมการทำความสะอาดให้ครบ
  - แผนที่เกี่ยวข้อง: ทุกระยะที่มีคอนโทรลเลอร์เพิ่ม
  - แนวทางรีแฟกเตอร์: สร้างวงจรชีวิตเดียวสำหรับสถานะ POS ทั้งหมด

### 11.2 ตัวช่วยด้าน UI

- `_gradientIcon()` และ `_gradientText()`
  - หน้าที่ปัจจุบัน: สร้างเอกลักษณ์ภาพแบบไล่เฉดสี
  - สิ่งที่ดี: ทำให้ POS ดูเป็นระบบเดียวกัน
  - สิ่งที่ยังขาด: ยังเป็นตัวช่วยภายในไฟล์ ไม่สามารถนำกลับใช้ได้ง่าย
  - แผนที่เกี่ยวข้อง: ความสม่ำเสมอของ UX/UI, ระบบดีไซน์
  - แนวทางรีแฟกเตอร์: ย้ายเป็นวิดเจ็ตใช้ร่วมกัน เช่น `AppGradientIcon`, `AppGradientText`

- `_focusSearchField()`
  - หน้าที่ปัจจุบัน: ขอโฟกัสไปที่ช่องค้นหา
  - สิ่งที่ดี: ลดอุปสรรคสำหรับแคชเชียร์
  - สิ่งที่ยังขาด: ยังไม่รองรับกระแสสแกนบาร์โค้ด/รหัสสินค้า
  - แผนที่เกี่ยวข้อง: ตัวเลือกสินค้า, กระแสบาร์โค้ด
  - แนวทางรีแฟกเตอร์: ให้คอนโทรลเลอร์เดียวดูแลโหมดค้นหาหลายแบบ

### 11.3 การโหลดข้อมูลและกระแสแคตตาล็อก

- `_loadData()`
  - หน้าที่ปัจจุบัน: โหลดสินค้าและหมวดหมู่พร้อมกันจาก `InventoryService`
  - สิ่งที่ดี: เรียบง่ายและตรงจุด
  - สิ่งที่ยังขาด: การจัดการข้อผิดพลาด, ลองใหม่, แคช, การแบ่งหน้า, การโหลดโครงกระดูก
  - แผนที่เกี่ยวข้อง: ตัวเลือกสินค้า, การเพิ่มประสิทธิภาพ, ซิงค์สต็อก
  - แนวทางรีแฟกเตอร์: แยกเป็น `พื้นที่เก็บแคตตาล็อก POS` + การโหลดแบบทีละขั้น (`หมวดหมู่` → `สินค้า` → `กฎภาษี`)

- `_filteredProducts`
  - หน้าที่ปัจจุบัน: กรองตามหมวดหมู่และคำค้นหา
  - สิ่งที่ดี: เป็นแกนของกระแสการเลือกสินค้า
  - สิ่งที่ยังขาด: บาร์โค้ด, ตัวกรองด่วน, รายการโปรด, สินค้าขายดี, ป้ายสต็อกต่ำ
  - แผนที่เกี่ยวข้อง: ตัวเลือกสินค้า, ค้นหาด่วน, กระแสบาร์โค้ด
  - แนวทางรีแฟกเตอร์: ย้ายตรรกะไปโมเดลมุมมอง / ผู้ให้บริการ เพื่อรองรับโหมดตัวกรองหลายแบบ

- `_getCategoryIcon(name)`
  - หน้าที่ปัจจุบัน: แมปชื่อหมวดเป็นไอคอน
  - สิ่งที่ดี: ช่วยให้แถบหมวดอ่านง่าย
  - สิ่งที่ยังขาด: การจับคู่ข้อความแบบฮาร์ดโค้ดทำให้เปลี่ยนชื่อหมวดแล้วไอคอนเพี้ยน
  - แผนที่เกี่ยวข้อง: UX หมวดหมู่, การจัดกลุ่มเมนู
  - แนวทางรีแฟกเตอร์: เก็บข้อมูลเมตาดาต้าของไอคอนในฐานข้อมูลหรือการตั้งค่าของหมวด

### 11.4 ตะกร้าและเครื่องงานราคา

- `_addToCart(product)`
  - หน้าที่ปัจจุบัน: คำนวณกฎภาษี, แคชกฎต่อหมวด, เพิ่มสินค้าเข้าตะกร้าหรือเพิ่มจำนวน
  - สิ่งที่ดี: มีแคชกฎภาษีและรองรับการเพิ่มสินค้าซ้ำ
  - สิ่งที่ยังขาด: สแนปชอตรายการ, การตรวจสอบสต็อก, ส่วนลดระดับรายการ, หมายเหตุรายการ, บริบทออเดอร์, การไม่เปลี่ยนแปลงข้อมูลต้นฉบับ
  - แผนที่เกี่ยวข้อง: เครื่องงานตะกร้าและราคา, นโยบายภาษี, การจัดการส่วนลด, การจองสต็อก
  - แนวทางรีแฟกเตอร์: สร้างโมเดล `PosCartItem` แยกจากสินค้า, เก็บสแนปชอตของ ชื่อ/ราคา/ภาษี/หน่วย/หมวด และห้ามเปลี่ยนแปลงข้อมูล `product` โดยตรง

- `_removeFromCart(index)`
  - หน้าที่ปัจจุบัน: ลบรายการด้วยลำดับ
  - สิ่งที่ดี: เข้าใจง่าย
  - สิ่งที่ยังขาด: ใช้ลำดับทำให้เปราะบางเมื่อรายการเปลี่ยนลำดับ
  - แผนที่เกี่ยวข้อง: การจัดการตะกร้า, การสนับสนุนพัก/เรียกบิลคืน
  - แนวทางรีแฟกเตอร์: ลบด้วย `cartLineId` แทนลำดับ และเตรียมการเรียกคืนได้ในอนาคต

- `_updateQty(index, delta)`
  - หน้าที่ปัจจุบัน: เพิ่ม/ลดจำนวน และลบถ้าจำนวน <= 0
  - สิ่งที่ดี: เหมาะกับ POS ที่ต้องเร็ว
  - สิ่งที่ยังขาด: กฎจำนวนสูงสุด/ต่ำสุด, การป้องกันสต็อก, การรองรับแยกรายการ
  - แผนที่เกี่ยวข้อง: เครื่องงานตะกร้าและราคา, ซิงค์สต็อก, แยกบิล
  - แนวทางรีแฟกเตอร์: ตรวจสอบก่อนเปลี่ยนจำนวน และให้รู้แหล่งที่มาของข้อจำกัดจากสต็อกสินค้า

- `_subtotal`, `_discount`, `_preTaxTotal`, `_taxAmount`, `_avgTaxRate`, `_serviceAmount`, `_netTotal`
  - หน้าที่ปัจจุบัน: รวมยอดเงินและภาษีแบบภาพรวม
  - สิ่งที่ดี: แยกยอดสำคัญได้ชัดเจน
  - สิ่งที่ยังขาด: ส่วนลดระดับรายการ, โมเดลภาษีรวม/แยก, ยอดชำระแล้ว/ยอดคงเหลือ, นโยบายค่าบริการตามสาขา
  - แผนที่เกี่ยวข้อง: เครื่องงานตะกร้าและราคา, เครื่องงานส่วนลด, นโยบายภาษี, เครื่องงานค่าบริการ, กระแสสถานะการชำระเงิน
  - แนวทางรีแฟกเตอร์: ย้ายการคำนวณไป `PosPricingService` และสร้าง `PosOrderSummary` ที่มี `subtotal`, `discountTotal`, `taxTotal`, `serviceTotal`, `grandTotal`, `paidTotal`, `balanceDue`

### 11.5 เลย์เอาต์และการนำทาง

- `build(context)`
  - หน้าที่ปัจจุบัน: สร้างโครงหลัก แบ่งพื้นที่เป็นแถบข้าง + แผงหลัก
  - สิ่งที่ดี: เหมาะกับหน้าจอ POS ขนาดใหญ่
  - สิ่งที่ยังขาด: สถานะข้อผิดพลาด, แถบบริบทออเดอร์, จุดเปลี่ยนเลย์เอาต์ตามขนาดจอ, แถบปุ่มด้านล่าง
  - แผนที่เกี่ยวข้อง: รีแฟกเตอร์เลย์เอาต์ POS ทั้งหมด, ชั้นข้อมูลบริบทออเดอร์
  - แนวทางรีแฟกเตอร์: แตก UI เป็นแผงย่อยตามงานจริง แล้วให้แต่ละแผงรับสถานะที่จำเป็นเท่านั้น

- `_buildLeftIconBar()` และ `_buildSidebarIcon()`
  - หน้าที่ปัจจุบัน: สร้างหมวดหมู่ด้านซ้ายและปุ่มเลือก
  - สิ่งที่ดี: กระชับ, ใช้นิ้วสัมผัสง่าย, มีคำอธิบาย
  - สิ่งที่ยังขาด: ป้ายจำนวนสินค้า, รายการโปรด, หมวดปักหมุด, แยกหมวดขายกับหมวดผู้ดูแล
  - แผนที่เกี่ยวข้อง: แถบหมวดหมู่, การจัดกลุ่มเมนู
  - แนวทางรีแฟกเตอร์: เพิ่มข้อมูลเมตาดาต้าต่อหมวดและแยกแหล่งข้อมูลระหว่างหมวดที่ขายได้กับหมวดทั้งหมด

- `_buildHeader()` และ `_headerChip()`
  - หน้าที่ปัจจุบัน: แสดงร้าน, โต๊ะตัวอย่าง, ผู้ใช้, วันที่, เวลา, ปุ่มย้อนกลับ
  - สิ่งที่ดี: เป็นแถบบริบทขั้นต้น
  - สิ่งที่ยังขาด: ประเภทออเดอร์, ลูกค้า, โต๊ะจริง, สถานะออเดอร์, สถานะกะ
  - แผนที่เกี่ยวข้อง: ชั้นข้อมูลบริบทออเดอร์
  - แนวทางรีแฟกเตอร์: เปลี่ยนส่วนหัวให้เป็นแถบบริบทที่จัดการสถานะได้ สะท้อนสภาพบิลจริง

- `_buildTopAndMiddleRow()`
  - หน้าที่ปัจจุบัน: จัดเลย์เอาต์โซน 1–4 แบบ 7:3
  - สิ่งที่ดี: โครงสร้างชัดสำหรับ POS จอใหญ่
  - สิ่งที่ยังขาด: ยังแข็งทื่อเมื่อจะเพิ่มคิวพักบิล, ลิ้นชักออเดอร์, แผงลูกค้า
  - แผนที่เกี่ยวข้อง: ออกแบบเลย์เอาต์ใหม่
  - แนวทางรีแฟกเตอร์: แตกเป็นวิดเจ็ตแผงและทำเลย์เอาต์ตามจุดเปลี่ยนขนาดจอ

### 11.6 การ์ดสรุปยอดและโซนชำระเงิน

- `_buildZone1()`
  - หน้าที่ปัจจุบัน: แสดงยอดก่อนภาษี, แถบส่วนลด, ยอดรวม
  - สิ่งที่ดี: สื่อยอดหลักก่อนคิดภาษีชัดเจน
  - สิ่งที่ยังขาด: ส่วนลดจริง, สรุปยอดระดับรายการ
  - แผนที่เกี่ยวข้อง: การจัดการส่วนลด, สรุปออเดอร์
  - แนวทางรีแฟกเตอร์: เปลี่ยนเป็น `OrderSummaryCard` ที่ดึงข้อมูลจากเครื่องงานราคา

- `_discountRow()` และ `_infoRow()`
  - หน้าที่ปัจจุบัน: ตัวช่วยสำหรับแสดงบรรทัดยอดเงิน
  - แนวทางรีแฟกเตอร์: รวมกับตัวจัดรูปแบบเงินและคอมโพเนนต์สรุปกลาง

- `_buildZone2()`
  - หน้าที่ปัจจุบัน: แสดงยอดสุทธิ, ภาษี, ค่าบริการ
  - สิ่งที่ดี: ยอดสุทธิเด่นและอ่านง่าย
  - สิ่งที่ยังขาด: ยอดชำระแล้วและยอดคงเหลือ
  - แผนที่เกี่ยวข้อง: กระแสสถานะการชำระเงิน, UI การเรียกเก็บ
  - แนวทางรีแฟกเตอร์: แสดงยอดที่ต้องชำระจริงและยอดคงเหลือร่วมด้วย

- `_buildZone3()` และ `_paymentButton()`
  - หน้าที่ปัจจุบัน: แสดงวิธีชำระเงินและเปิดหน้าต่างยืนยัน
  - สิ่งที่ดี: เข้าใจง่ายสำหรับกระแสง่าย
  - สิ่งที่ยังขาด: แยกการชำระ, ชำระบางส่วน, เลขอ้างอิง, ยอดเงินทอน, หมายเหตุการชำระ
  - แผนที่เกี่ยวข้อง: กระแสสถานะการชำระเงิน, แยกการชำระ
  - แนวทางรีแฟกเตอร์: เปลี่ยนจากปุ่มตามวิธีการเป็นแผงกระทำการชำระที่รับยอด/วิธีชำระ/ยอดคงเหลือ

### 11.7 ตัวเลือกสินค้าและแผงตะกร้า

- `_buildZone4()`
  - หน้าที่ปัจจุบัน: กริดสินค้า + ค้นหา + ปุ่มสแกน
  - สิ่งที่ดี: เป็นพื้นที่หลักของการเลือกสินค้า

  - สิ่งที่ดี: สถานะว่างดีและเข้าใจง่าย

## 12) โมเดลการรับผิดชอบบิลสำหรับลูกค้าเดินเข้า / ลูกค้าทั่วไป

เพื่อให้ตรวจสอบย้อนหลังได้ชัดเจน ระบบ POS ของ Tree Law Zoo Valley ควรแยก 3 บทบาทออกจากกัน:

- **ลูกค้า**
  - ใช้สำหรับผู้ซื้อสินค้า/บริการ
  - ถ้าเป็นลูกค้าที่เลือกจากระบบ ให้ผูกกับ `customer_user_id` หรือ `pos_customers`
  - ถ้าเป็นลูกค้าเดินเข้า อาจเว้นว่างหรือใช้บันทึกลูกค้าเฉพาะ

- **พนักงานผู้รับผิดชอบ / พนักงานขาย**
  - ต้องมีทุกบิล
  - ผูกกับ `responsible_user_id` ใน `pos_orders`
  - ใช้ในระบบบุคคลเป็นสวิตช์เปิด/ปิด `is_sales_staff_group` หรือ `is_sales_staff`

- **แคชเชียร์**
  - คนที่กดชำระเงินหรือบันทึกบิล
  - เก็บเป็น `cashier_user_id` เพื่อดูว่าใครทำรายการ

### ตารางที่เกี่ยวข้อง

- `user_groups`
  - `is_customer_group`
  - `is_sales_staff_group`

- `users`
  - `is_sales_staff`

- `pos_orders`
  - `order_type`
  - `responsible_user_id`
  - `responsible_user_name`
  - `cashier_user_id`
  - `cashier_user_name`
  - `customer_user_id`
  - `customer_name`

- `pos_customers`
  - รองรับลูกค้าเดินเข้าและลูกค้าที่ผูกกับผู้ใช้

### กระแส UX ที่ควรยึด

1. เปิดบิล
2. เลือกพนักงานผู้รับผิดชอบจากส่วนหัวของ POS
3. เลือกหรือเว้นว่างลูกค้าตามประเภทบิล
4. กดชำระเงิน
5. บันทึกออเดอร์พร้อมการติดตามพนักงาน

### หลักการสำคัญ

- บิลลูกค้าเดินเข้า **ต้องมีพนักงานผู้รับผิดชอบเสมอ**
- ลูกค้าและพนักงาน **ห้ามใช้แทนกัน**
- ระบบบุคคลใช้สวิตช์เปิด/ปิดเพื่อระบุกลุ่มที่ใช้เป็นลูกค้าหรือพนักงานขายได้
- POS ใช้ข้อมูลนี้เพื่อกรองรายชื่อและบังคับกระแสการชำระเงิน

## 13) การเชื่อมที่นั่ง/โต๊ะสำหรับแต่ละร้าน

ถ้าร้านมีหน้า "ที่นั่ง/โต๊ะ" แยกตามสาขาหรือโซน ควรเชื่อมหน้านั้นเข้ากับ POS โดยตรง เพื่อให้กระแสการเปิดบิลเป็นแบบปฏิบัติการจริงมากกว่าการเลือกด้วยมือทุกครั้ง

### เป้าหมาย

- แตะโต๊ะ/ที่นั่งแล้วเปิดบิล POS ได้ทันที
- เมื่อเปิดบิลทานในร้าน ให้ระบบเติมข้อมูลโต๊ะอัตโนมัติ
- รองรับการย้ายโต๊ะ, พักบิล, และเรียกบิลคืน
- ผูกสถานะโต๊ะกับออเดอร์ปัจจุบันได้แบบเรียลไทม์

### ตารางที่ควรมี

- `pos_tables`
  - `id`
  - `store_id`
  - `zone`
  - `table_code` หรือ `seat_code`
  - `table_name`
  - `capacity`
  - `status` (`available`, `occupied`, `reserved`, `cleaning`, `disabled`)
  - `current_order_id`
  - `current_customer_id`
  - `current_responsible_user_id`
  - `updated_at`

- `pos_table_sessions`
  - ใช้เก็บรอบการใช้งานโต๊ะ
  - เหมาะกับการวัดเวลาทานในร้าน, ย้ายโต๊ะ, และเปิดบิลคืน
  - ฟิลด์แนะนำ:
    - `table_id`
    - `order_id`
    - `opened_by`
    - `opened_at`
    - `closed_at`
    - `status`

- `pos_order_events`
  - ใช้บันทึกเหตุการณ์สำคัญ เช่น เปิดโต๊ะ, ย้ายโต๊ะ, พักบิล, เรียกบิลคืน, ชำระเงิน, ปิดบิล

### กระแส UX ที่ควรใช้

1. เปิดหน้าที่นั่ง/โต๊ะ
2. เลือกโต๊ะที่ว่างหรือโต๊ะที่มีบิลค้างอยู่
3. ระบบส่งบริบทไป POS:
   - `order_type = dine_in`
   - `table_id`
   - `table_name` / `table_code`
   - `customer_user_id` ถ้ามี
   - `responsible_user_id` ถ้ามีคนเปิดบิลไว้แล้ว
4. POS เปิดขึ้นพร้อมสรุปโต๊ะและบิล
5. ผู้ใช้งานเลือก/ยืนยันพนักงานผู้รับผิดชอบ
6. เพิ่มสินค้าและชำระเงิน
7. ปิดบิลแล้วอัปเดตสถานะโต๊ะกลับเป็นว่าง

### พฤติกรรมสำคัญที่ควรมี

- **การแตะโต๊ะ**
  - ถ้าโต๊ะว่าง → สร้างบิลใหม่
  - ถ้าโต๊ะมีบิลอยู่ → เปิดบิลเดิม

- **ย้ายโต๊ะ**
  - เปลี่ยน `table_id` ในออเดอร์และอัปเดตเซสชัน/เหตุการณ์

- **พักบิล / เรียกบิลคืน**
  - หากลูกค้าออกไปชั่วคราว ให้บันทึกสถานะโต๊ะและบิลไว้

- **กระแสลูกค้าเดินเข้าใช้ร่วมกัน**
  - ถ้าเป็นลูกค้าเดินเข้าที่ไม่มีโต๊ะ ให้ยังบังคับเลือกพนักงานผู้รับผิดชอบเหมือนเดิม

### สิ่งที่ควรเพิ่มใน `pos_orders`

- `table_id`
- `table_name`
- `table_status_snapshot`
- `opened_from_seating_page` (บูลีน)

### สรุปการเชื่อม

- หน้าที่นั่ง/โต๊ะ = จุดเริ่มต้นของกระแสทานในร้าน
- หน้า POS = จุดจัดการสินค้าและชำระเงิน
- `pos_tables` = แหล่งข้อมูลหลักของโต๊ะ/ที่นั่ง
- `pos_orders` = แหล่งข้อมูลหลักของบิล
- `pos_table_sessions` / `pos_order_events` = ประวัติการใช้งานและการย้ายสถานะ

### 14.2 P5-6b: End-of-Day (EOD) / Daily Settlement Flow

**เป้าหมาย**: ปิดยอดบัญชีประจำวันแบบครบวงจร ให้ยอดขาย-เงินสด-โอน-คืนเงิน ตรงกับความเป็นจริงทุกวัน

**ตารางใหม่**: `pos_daily_settlements`
- `id`, `settlement_date` (unique), `store_id`
- `total_sales`, `total_cash`, `total_cashless`, `total_refunds`, `total_voids`
- `total_discounts`, `total_loyalty_redeemed`, `total_tax`, `total_service_charge`
- `expected_cash`, `counted_cash`, `cash_difference`
- `shift_ids` (JSONB — กะทั้งหมดที่รวมในวันนั้น)
- `status` (`draft` / `closed` / `reopened`), `closed_by`, `closed_at`, `note`

**Flow UI**:
1. ปุ่ม "ปิดยอดประจำวัน" ในหน้ารายงาน (แสดงเฉพาะผู้มีสิทธิ์ `pos_eod_close`)
2. ระบบตรวจสอบเงื่อนไขก่อนปิด: ทุกกะต้องปิดแล้ว, ไม่มีบิลค้างชำระ, ไม่มีบิลพักค้างคืน (หรือให้ยืนยัน carry-over)
3. แสดงหน้าสรุป: ยอดขายแยกช่องทาง, คืนเงิน/ยกเลิก, ส่วนลด, ภาษี, ค่าบริการ, แต้มที่แลก
4. กรอกเงินสดนับจริง → คำนวณเงินขาด/เกินอัตโนมัติ → บังคับใส่เหตุผลถ้าต่างเกิน threshold
5. ยืนยันด้วย PIN ผู้จัดการ → บันทึก settlement → พิมพ์/บันทึก PDF รายงาน EOD
6. เปิดยอดใหม่ (reopen) ได้เฉพาะ admin พร้อม audit log

### 14.3 แผนความปลอดภัย (Security) — เครื่องมือฟรีทั้งหมดช่วงพัฒนา

#### ก. ชั้นฐานข้อมูล (Supabase ฟรี tier)

| # | มาตรการ | วิธีทำ (ไม่มีค่าใช้จ่าย) |
|:---:|:---|:---|
| S-1 | **RLS ทุกตาราง `pos_*`** ✅ | เปิด Row Level Security + policy ตาม role ทุกตาราง โดยเฉพาะ `pos_orders`, `pos_shifts`, `pos_refunds`, `pos_daily_settlements` |
| S-2 | **Audit log แบบ insert-only** ✅ | RLS ห้าม `UPDATE`/`DELETE` บน `pos_audit_logs` และ `pos_order_status_log` — แก้ไข/ลบไม่ได้แม้เป็น admin |
| S-3 | **ตัดสต็อก/ปิดบิลผ่าน RPC เท่านั้น** | ใช้ Postgres function (`SECURITY DEFINER`) แทน client-side write ตรง ป้องกันการปลอมยอดจาก client |
| S-4 | **Idempotency key ทุกธุรกรรมเงิน** | ใส่ unique key ต่อการชำระ/คืนเงิน ป้องกัน double-submit (แบบเดียวกับ gate scanner replay) |

#### ข. ชั้นแอป (Flutter)

| # | มาตรการ | วิธีทำ (ไม่มีค่าใช้จ่าย) |
|:---:|:---|:---|
| S-5 | **Manager PIN ต้อง hash** ✅ | เก็บ PIN ด้วย bcrypt/SHA-256+salt ใน DB ห้ามเก็บ plaintext, จำกัดผิดได้ 5 ครั้ง/5 นาที (lockout ฝั่ง DB) |
| S-6 | **Action-level permission ให้ครบ** ✅ | ใช้ `checkPermissionAndExecute()` ครอบทุกปุ่มเสี่ยง: void, refund, ส่วนลด manual, เปิดลิ้นชัก, EOD, reopen settlement |
| S-7 | **ห้าม hardcode คีย์** | ย้าย Supabase URL/anon key ไป `--dart-define` หรือ `.env` (เพิ่มใน `.gitignore`) — anon key ใช้ได้แต่ต้องพึ่ง RLS เป็นกำแพงจริง |
| S-8 | **Session timeout** | Auto-logout/lock หน้า POS เมื่อไม่มีการใช้งาน 15 นาที บังคับใส่ PIN กลับเข้า |
| S-9 | **Validate input ฝั่ง client + server** | จำนวนเงิน/แต้ม/จำนวนสินค้า ห้ามติดลบ, จำกัด max ต่อรายการ ทั้งใน Flutter และ DB constraint (`CHECK`) |
